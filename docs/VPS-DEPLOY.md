# Сайт и парольная админка на VPS в России

**Статус: адаптер подготовлен и проверен локально; сервер ещё не создан, перенос и DNS-переключение не выполнены.** Рекомендуемая площадка после выбора владельцем отдельного провайдера — Beget VPS/VDS в российском регионе. Selectel тоже совместим. Нужны Ubuntu 24.04 LTS, Node.js 24 LTS, Python 3.12+, Nginx, HTTPS, от 2 ГБ RAM и 20 ГБ диска. Цену и регион проверять перед оплатой; обычный статический хостинг не заменяет Node.js-сервис.

## Архитектура

`vps/server.mjs` использует тот же серверный код авторизации, API, проверок прав и HTML, что действующий Worker. Вместо Cloudflare используются локальные статические файлы и SQLite (`node:sqlite`, Node 24). npm-пакеты для работы VPS не нужны. Сохраняются `/admin/`, логин/пароль, адреса проектов, внешний вид и моментальная публикация. Сессии Cloudflare не переносятся: потребуется войти заново.

Тексты и фотографии по-прежнему сначала записываются в GitHub, затем в локальную опубликованную копию. **Публичный сайт не зависит от доступности Cloudflare или GitHub у посетителя**, но для редактирования сервер должен иметь доступ к GitHub. Полностью автономное файловое CMS и автоматическая репликация двух серверов здесь не реализованы.

## Подготовка без переключения домена

1. Создать VPS в РФ. Настроить SSH по ключу, межсетевой экран: снаружи нужны 80/443 и ограниченный доступ администратора по SSH. Node слушает **только `127.0.0.1:3000`**; не открывать 3000 в интернет.
2. Установить Node.js **24 LTS** из проверенного источника, Python 3, Git, Nginx и Certbot. Проверить `/usr/bin/node --version`: unit использует этот путь. Проверить соединение VPS с `api.github.com` и `codeload.github.com` по HTTPS.
3. Создать системного пользователя `epiphany` без интерактивного входа, root-owned `/opt/epiphany/releases/` и `/etc/epiphany/` с правами 700. Приложение не должно изменять свой код или конфигурацию.
4. Клонировать репозиторий с **полной историей** в отдельный каталог. Перед финальной сборкой остановить редактирование в старой панели, скачать JSON/ZIP, получить последние коммиты. Не заменять `content/` старой локальной копией. Свежий checkout уже содержит сохранённые в старой панели тексты и фотографии независимо от ускоряющей копии Cloudflare.
5. Собрать проверенный выпуск из полного checkout, например `/opt/epiphany/releases/<commit>/`:

```sh
python3 scripts/design-inventory.py --check
node --test tests/*.test.mjs
python3 -m unittest discover -s tests -p 'test_*.py'
python3 scripts/build.py --site-url https://epiphany-int.ru/ --output _site-vps --admin-mode password
python3 scripts/audit-secrets.py --frontend _site-vps
```

В выпуске оставить `site-worker/src/`, `password-admin/schema.json`, `vps/`, готовый `_site-vps/` и `site-worker/generated/site.json`. Для согласования публикаций используются SHA файлов и история коммитов. Nginx **не** раздаёт исходники checkout.

6. Скопировать `vps/server.env.example` в `/etc/epiphany/server.env` (`root:root`, 600), заполнить на сервере. Это EnvironmentFile systemd: `$` в хеше записывается буквально; **не** выполнять `source server.env` в shell. Не помещать секреты в Git, аргументы команд, чат или публичные каталоги.

   Хеш можно получить локально через `docs/create-admin-password.html` с прежним паролем. GitHub-токен — отдельный fine-grained, только к `design.site`, Contents: Read and write. Пользователю админки вход в GitHub не нужен. Сохранить `ADMIN_USERNAME=admin`, `CONTENT_BRANCH=main`, `SITE_ORIGIN=https://epiphany-int.ru` без завершающего `/`.

7. Создать `/opt/epiphany/current` как ссылку на выпуск. Установить `vps/epiphany.service` в `/etc/systemd/system/`, выполнить `systemctl daemon-reload` и `systemctl enable --now epiphany`. systemd создаст `/var/lib/epiphany/` (700); приложение создаст SQLite с правами 600. Проверить журнал без вывода значений окружения.
8. Настроить Nginx по `vps/nginx.conf.example`. Host/HTTPS/IP **перезаписываются прокси**, а не берутся у посетителя. Не включать прокси-кэш HTML/API. Пример отключает access log; срок хранения error log нужно задать и отразить в политике.

## HTTPS и проверка до переключения

Получить действительный сертификат `epiphany-int.ru`. Предпочтителен DNS-01 до переключения A-записи: TXT вносится в текущий авторитетный DNS. Ручной DNS-01 не обеспечивает автоматическое продление: до запуска настроить его через DNS API либо HTTP-01 после перехода домена на VPS. Закрытый ключ остаётся на сервере.

Не активировать TLS-конфиг с несуществующими файлами: сначала сертификат, затем `nginx -t` и reload. После переключения HTTP-01 обслуживается `/var/www/letsencrypt` из примера; проверить `certbot renew --dry-run` с фактическим способом выпуска.

Без изменения общего DNS проверить VPS через локальное сопоставление домена с IP (hosts или `curl --resolve epiphany-int.ru:443:IP`). Так сохраняются правильные origin и сертификат; голый IP/HTTP не подходят для Secure cookie. Проверить все страницы/проекты/фото, мобильное меню, вход, удаление символа и повторное сохранение, новый проект/фото, JSON/ZIP экспорт, выход, перезапуск. Проверки записей затрагивают настоящий GitHub: использовать согласованный временный тестовый проект и удалить его штатно. Сравнить контент/фото со свежим checkout. Проверить несколько российских сетей.

## Резервирование и восстановление

Online backup SQLite создаётся встроенным API с проверкой целостности, а не копированием одного активного файла без WAL:

```sh
sudo /usr/bin/node /opt/epiphany/current/vps/backup.mjs /var/lib/epiphany/state.sqlite /var/backups/epiphany/BEFORE-CUTOVER.sqlite
```

Назначение должно быть новым файлом: старые копии не перезаписываются. Каталог копий — 700, файлы — 600. Они содержат сессии и требуют защиты. До запуска настроить ежедневное расписание с уникальными именами, хранение, например 30 суток, и **зашифрованную копию вне VPS**, включая `/etc/epiphany/server.env`, TLS-конфигурацию и идентификатор выпуска. GitHub не заменяет такую копию. Автоматическая отправка на второй сервер пока не подключена.

Пробное восстановление: развернуть тот же выпуск и копию БД на закрытом экземпляре, не разрешая ему запись в рабочий GitHub; проверить целостность, количество записей, HTML/медиа, вход и экспорт. Для записей использовать отдельный тестовый репозиторий/токен. Не запускать два независимых редактора рабочего контента.

При аварии остановить основной сервис, сохранить текущую БД с WAL/SHM, заменить проверенной копией; старые WAL/SHM удалять только после сохранения и остановки. Выставить `epiphany:epiphany`, 600, запустить и проверить. Старая БД не откатывает GitHub: сверить более свежие изменения и собрать новый baseline. Восстановленные сессии могут снова действовать до истечения срока; смена хеша пароля отзывает их.

## Схема и откат

Начальная схема — `vps/sql/001-up.sql`, `user_version=1`: `kv` и `alarms`. Составной первичный ключ `(namespace,key)` индексирует точечное чтение и списки префиксов. Время — UTC epoch milliseconds. Пользовательские данные не интерполируются в SQL. RLS нет: файл доступен серверу, API проверяет сессию и права в общем коде.

`001-down.sql` приложен и проверен на одноразовой тестовой БД. Он **удаляет данные**: для живого сайта применяется восстановление проверенной копии, а не down «для отката кода». Неизвестная версия схемы останавливает запуск. Откат кода: вернуть ссылку `current` к совместимому выпуску, перезапустить, сохраняя БД. До смены схемы делать копию и проверять совместимость. **Миграция/откат на копии production ещё не проверены.**

## Переключение и обновления

1. После проверок переключить A домена на VPS, удалить старое Worker-назначение и конфликтующую AAAA, если у VPS нет IPv6. Две A-записи не заменяют управляемое резервирование.
2. Для полного отказа от Cloudflare подготовить записи в Timeweb/выбранном DNS, затем сменить NS у регистратора. До распространения NS старый и новый DNS должны вести на VPS; учесть почтовые записи и проверки владения. Не отключать прежний сайт заранее.
3. Проверить HTTPS/админку на домене из РФ, продление сертификата, резервирование и восстановление. Опубликовать юридические документы с фактическим хостингом и сроками логов.
4. Затем выключить старые Cloudflare/GitHub Pages публикации и отозвать ненужные ключи; прежние данные не удалять до проверки копий.

Сохранения в панели VPS видны сразу и переживают рестарт. Прямые изменения в GitHub требуют нового выпуска на VPS: автоматическая доставка ещё не подключена. Старые Actions работают для Cloudflare до отдельного переключения. Выпуск обновлять через новый каталог и атомарную смену ссылки `current`, не через `git pull` внутри обслуживаемого каталога. Сначала резервировать SQLite и учитывать новые CMS-коммиты.

`tests/vps.test.mjs` проверяет HTTP, отказ неправильному host/HTTPS, вход, мгновенную публикацию, транзакции/rollback/1005 ключей, изоляцию, истечение сессий, восстановление контента/фото/сессии из online backup и выход. Данные синтетические, GitHub подставной. Это не проверка живого VPS, DNS, Nginx или связи Beget с GitHub.
