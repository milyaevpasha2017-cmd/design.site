# Заявки с сайта

Основной сайт на Timeweb принимает POST /api/leads с именем, контактом и
необязательным описанием. Подтверждение показывается только после записи в SQLite.
Копировать обращение или открывать почтовую программу больше не требуется.
Контакты для прямого обращения по-прежнему доступны рядом с формой.

Администратору доступен /admin/leads.html (ссылка «Заявки клиентов» в панели).
Заявки расположены от новых к старым с загрузкой следующих страниц; статусы:
«Новая», «В работе», «Завершена». Удаление требует подтверждения. Контент отображается
как текст, без выполнения HTML. Данные заявок не отправляются в GitHub и не входят
в публичный экспорт контента; SQLite backups содержат их вместе с сессиями.
Схема БД остаётся v1: используется отдельное пространство ключей epiphany-leads.

Публичная отправка ограничена same-origin HTTPS, JSON до 16 КБ, длинами полей,
скрытым полем для простых ботов, лимитами 5 обращений за 15 минут / 20 за сутки
по хешу IP, 100 за час суммарно. Эти ограничения не заменяют полноценную защиту
от распределённого спама. UUID запроса исключает повторное сохранение при сетевом
повторе, в том числе при одновременных запросах. Административные чтение/изменение/
удаление защищены существующей сессией; записи — также Origin и CSRF.

## Уведомления в Telegram и резервная почта

1. Владелец или дизайнер создаёт отдельного бота через https://t.me/BotFather → /newbot.
2. На VPS после обновления запускает:
   `python3 /opt/epiphany/current/vps/setup-telegram.py`.
3. Вставляет токен в скрытый запрос. Токен не вводить в аргументы команд, чат,
   GitHub-код или скриншоты. Установщик проверяет getMe и просит написать /start боту.
4. Дизайнер @paulinaepifanova (актуальный Telegram из контактов сайта) запускает бота. Установщик принимает только её личный чат, сверяя username с текущими контактами сайта; выбирается её chat ID. Установщик посылает тестовое
   уведомление и записывает TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID в root-owned
   /etc/epiphany/server.env (600), сохраняя остальные настройки.
5. Выполняет `systemctl restart epiphany`. Отправляет тестовую заявку через сайт,
   проверяет панель и получение уведомления.

Для обычной формы и прежних заявок Telegram получает только номер и ссылку на админку. Для новых заявок квиза с явным согласием на передачу Telegram получает имя, контакт и результаты; подробности — в разделе ниже.
Без настроек доставки форма работает и сохраняет заявки; панель явно сообщает, какие каналы настроены. После подключения ожидающие уведомления отправляются.

Фоновая задача каждые 30 секунд проверяет устойчивую очередь в SQLite. При недоступности API Telegram отправляется полная заявка на актуальный email из контактов сайта через SMTP. При ошибке обоих каналов — до 8 попыток с паузами,
затем ошибка видна в карточке заявки. Доставка Telegram — at-least-once: при обрыве
после принятия сообщения Telegram возможно повторное уведомление с тем же номером.
Состояние очереди переживает рестарты и обычные обновления кода. Ошибка Telegram
не пишет URL с токеном или персональные данные в логи. Серверные ключи и база
не включаются в архив frontend. Политика обработки данных требует актуальных
сведений об операторе и сроках хранения; черновик описания приведён в LEGAL-DRAFTS.md.

Проверки: реальные HTTP-запросы к временному VPS-приложению, авторизация/CSRF,
повторная отправка, ограничения, восстановление SQLite backup, очередь уведомлений
с подставным Telegram. Проверку настоящего получателя выполняет владелец при настройке.

Официальный API: https://core.telegram.org/bots/api#sendmessage

## Подключение резервной почты

На VPS выполнить `python3 /opt/epiphany/current/vps/setup-email.py`, ввести SMTP
отправляющего ящика и пароль приложения в скрытое поле. Получатель берётся из
текущих контактов сайта, включая более новые сохранения из админки. Установщик
проверяет отправку тестового письма, затем сохраняет настройки (root:root, 600).
Перезапустить `systemctl restart epiphany`. SMTP принимает только 465 с TLS или
587 с обязательным STARTTLS и проверкой сертификата. Секреты не выводятся в лог.
Необходимы реальные SMTP-доступы; наличие адреса в контактах само по себе их не даёт.

Когда Telegram подтверждает принятие сообщения, резервная почта не используется.
Сервис не определяет, прочитал ли дизайнер Telegram и доступен ли Telegram на её
телефоне. Резерв срабатывает при ошибке API/соединения, а не при отсутствии прочтения.
Статус «отправлено по почте» означает принятие письма SMTP, а не гарантированное
попадание во «Входящие»; проверить папку «Спам» при настройке. Сетевой обрыв после
принятия письма может привести к повторной доставке с тем же Message-ID.

Полные заявки резервной почты обрабатывает почтовый провайдер. По обычным уведомлениям Telegram
персональные поля не передаются. Уведомления со статусом ошибки можно поставить
в очередь заново кнопкой «Повторить уведомление».

Обращения к Telegram используют системный curl по IPv4 (установщик Python и runtime Node), сохраняя
api.telegram.org как TLS hostname и стандартную проверку сертификата. Это не меняет
общесистемные сетевые настройки. Отдельный прокси для Telegram не используется.

Токен Telegram передаётся curl через stdin-конфигурацию, не через argv или переменные
окружения. Ошибки curl не выводят stderr с возможным URL токена. Установщик сообщает
только числовой код curl либо безопасное описание ответа API. Проверка TLS включена,
редиректы не следуются. Curl может согласовать HTTP/2 с Telegram.

## Как посетитель находит форму

Кнопка «Оставить заявку» находится в закреплённой шапке всех публичных страниц; на узких экранах её подпись сокращается до «Заявка», полное доступное название сохранено. Кнопки обращения на главной, в услугах и нижних блоках ведут на `/contact/#brief-form`. После раскрытия формы JavaScript повторно разрешает якорь и переводит фокус на контейнер формы без автоматического открытия клавиатуры.

На странице контактов вводный текст и форма находятся рядом на широком экране; на телефоне форма идёт перед альтернативными контактами. Один экземпляр формы и прежний API/согласие/уведомления сохранены. Контактные ссылки и кнопка отправки не заменяют друг друга. При открытии мобильного меню фокус переводится на первый пункт, Escape возвращает его кнопке меню.


## Квиз: окно контактов и полное уведомление

С редакции согласия `2026-11-01-v2` новые заявки всплывающей формы квиза сохраняют `source=quiz` и `consent.telegramContent=true`. В их уведомление Telegram включаются имя, контакт, результаты и ссылка на закрытую админку. Обычные и прежние заявки остаются в режиме «номер + ссылка». Флажок нельзя добавить к уже принятой заявке повтором того же UUID: режим доставки входит в её отпечаток. Согласие с устаревшей версией отклоняется. SMTP по-прежнему не подключён.

## Запуск доставки и диагностика

После принятия новой заявки и после команды повтора уведомление отправляется сразу в фоне, без ожидания 30-секундного интервала и без задержки ответа формы. Интервал остаётся резервным механизмом. На запуске сервиса прежние pending-заявки однократно получают немедленную попытку с transportVersion=2; отправленные и окончательно failed-записи не переотправляются автоматически.

Бюджет внешнего сигнала — 25 секунд, curl — до 20 секунд при соединении до 10 секунд, аварийный таймер транспорта — 23 секунды. Это устраняет прежнее прерывание на восьмой секунде. В закрытой карточке показываются только безопасные коды причин (таймаут/сеть/отклонённый токен/чат/запрет/ограничение частоты), без токена, сырого ответа Telegram и содержимого заявки. Для pending и failed доступен ручной повтор. HTTP 429 учитывает retry_after в пределах часа.
