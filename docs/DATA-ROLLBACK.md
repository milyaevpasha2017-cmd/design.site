# Хранение и откат: фактическая архитектура

Для подготовленного, ещё не развёрнутого VPS-адаптера появилась собственная SQLite-схема с `001-up.sql`/`001-down.sql`, online backup и локальной проверкой восстановления. Это отдельный путь развёртывания, описанный в [VPS-DEPLOY.md](VPS-DEPLOY.md). Ниже описана действующая архитектура Cloudflare; перенос production ещё не выполнен.

У приложения нет Supabase/PostgreSQL, RLS или таблиц с бизнес-строками. Контент хранится как JSON/медиа в GitHub; Cloudflare Durable Objects используют управляемое SQLite-backed key/value storage для сессий и опубликованных версий.

## Что является миграцией

`site-worker/wrangler.toml`, тег `v1`: создание SQLite-backed класса `AdminState` через `new_sqlite_classes`. Это миграция инфраструктуры Cloudflare, а не SQL `CREATE TABLE` проекта. Пользовательских SQL-миграций и SQL-файлов отката в репозитории нет. Схема key/value хранится Cloudflare; записывать вымышленный `DROP TABLE` было бы неверно и опасно.

Изменения аудита добавляют поле SHA в ответ чтения, снимок SHA в модуль сборки и новые API/интерфейс. Формат существующих сохранённых сессий, метаданных публикации и блоков фотографий не изменяется. Отдельная миграция данных для этого обновления не нужна.

## Безопасный порядок отката кода

1. В новой панели скачать экспорт JSON и ZIP с фотографиями/исходниками. Они не включают серверные сессии и не являются полной копией Durable Objects.
2. Сохранить ID текущего и последнего стабильного развёртывания из Cloudflare Deployments. Выбирать стабильную версию после подключения `epiphany-int.ru`, с поддержкой `publish:*`, разбиения документов на блоки и действующими секретами.
3. Предпочтительно отменить проблемные изменения кода новым коммитом и запустить обычную публикацию с текущими Actions Variables. Не откатывать при этом `content/` и не выполнять force-push или `git reset --hard` поверх работ дизайнера.
4. Альтернатива для срочного восстановления — механизм Rollback в Cloudflare Deployments. Проверить у выбранной версии `SITE_ORIGIN=https://epiphany-int.ru`, действующие секреты, привязки `ASSETS` и `ADMIN_STATE`. Версия с origin workers.dev может сломать вход на домене.
5. После отката проверить главную, проект, вход, сохранение, удаление слов и выход. Проверить, что правки дизайнера сохранены.

Не добавлять `deleted_classes=["AdminState"]` для «отмены создания класса»: удаление класса может уничтожить его данные. Код, не понимающий уже записанный формат, сначала должен получить совместимость или преобразователь. Изменения секретов и их отзыв не откатываются возвращением Git-коммита.

## Что проверено и что нет

- Проверены сессии, их отзыв и публикации в локальном нативном workerd + SQLite Durable Object.
- Проверены сохранение при конфликтах SHA и переживание фоновой сборки.
- На 1005 синтетических проектах проверено чтение с переходом через границы 500/1000 записей.
- **Не получена копия живого Durable Object. Миграция инфраструктуры и её откат на копии production не проверены.** Экспорт JSON/ZIP нельзя представлять как такую проверку.
- Полный откат данных, восстановление живых SQLite объектов и проверка реальных провайдерских копий требуют доступа и отдельного плана. До этого пункт 5 не закрыт.

## Время, удаление, индексы

Сроки сессий и лимитов хранятся как Unix milliseconds UTC; время экспорта — ISO 8601 с `Z`. Профилей с часовыми поясами и напоминаний нет. Если появится PostgreSQL и планировщик, нужны timezone-aware даты, отдельная IANA timezone пользователя и сценарии DST; текущие timestamps не являются PostgreSQL `timestamptz`.

Точечные операции используют ключи `session:<hash>` и `attempt:<hash>`, опубликованные документы — `content:<path>`, их блоки — `document:<path>:<index>`, фото — `media:<path>`. Ключевое чтение и prefix/range list выполняет управляемое хранилище; собственных SQL-фильтров и индексных DDL нет. Полное чтение всех изменений публикаций и публичное портфолио растут с объёмом данных.

`DELETE /api/projects/<slug>` сейчас удаляет JSON из текущего дерева Git. Это **не soft delete**. История Git и фотографии остаются; корзины/восстановления в панели нет. `published=false` скрывает проект на сайте, но не защищает файлы. Аккаунтов посетителей и функции удаления аккаунта нет. Для строгого выполнения пункта 8 нужны отдельная корзина, восстановление, серверное исключение удалённых записей и согласованная политика удаления истории/медиа; RLS тут не заменяет эти механизмы.
